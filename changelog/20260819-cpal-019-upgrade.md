# Prepare the cpal 0.19 upgrade on a branch

## Task Specification

Follow-on from `20260819-cpal-upstream-update.md`, which moved spkrd
from the `knz/cpal` fork to released crates.io cpal 0.18.2 and
deferred the 0.19 migration.

User request: prepare the upgrade to cpal 0.19 on a branch.

0.19.0 is unreleased, so this means a git dependency on
`RustAudio/cpal` (default branch `master`, which contains the drain
work and is 6 commits ahead of `develop`). The branch is preparation
— not intended to merge until 0.19.0 ships to crates.io.

## Known scope (from the prior investigation)

Breaking changes that touch spkrd, per upstream `UPGRADING.md`:

1. `ErrorKind::Xrun` removed. Sites: `src/cpal_backend.rs:588`
   (the `Continues` match arm), `:921` (unit-test assertion), `:32`
   (module doc comment). Underruns now arrive as
   `CallbackInfo::xrun()` on the data callback. Verified that no
   former-Xrun condition is re-routed to another `ErrorKind`, so
   spkrd's catch-all `_ => Fatal` arm is not at risk.
2. `OutputCallbackInfo` merged into `CallbackInfo` — the data
   callback closure signature at `src/cpal_backend.rs:372`.
3. `StreamTrait::play` renamed to `start` (deprecated alias still
   compiles) — `src/cpal_backend.rs:435`.
4. Rust edition 2024 / MSRV 1.85 in cpal. Local toolchain 1.95, CI
   uses `stable`; not expected to be a blocker.

Opportunity, not a break:

5. `StreamTrait::stop(timeout)` performs a draining stop. Upstream
   closed issue #1190 with the PR that added it (#1258). #1190 is
   the pipewire-pulse truncation bug that `build_device_state` works
   around with `BufferSize::Fixed(sample_rate / 100)`, and that
   `run_stream` backstops with an unconditional 50 ms sleep before
   dropping the stream.

## Decisions

Both put to the user:

- **Drain scope: drain + revert `BufferSize` to `Default`.** The
  alternative considered was keeping `BufferSize::Fixed` on the
  grounds that a small buffer also bounds cancellation latency on
  client disconnect. The user chose the fuller revert; runtime
  testing below shows cancellation is in fact unaffected, so the
  concern did not materialise.
- **Pin: git URL, default branch,** not an explicit `rev`.
  `Cargo.lock` pins the exact revision regardless, so builds are
  reproducible; `cargo update -p cpal` moves it forward deliberately.

Structural choice: cpal is a *direct* dependency of spkrd, so the
branch points the dependency itself at git rather than reintroducing
a `[patch.crates-io]` section. `[patch]` exists to override
transitive dependencies and was only used before because the fork
had to satisfy an existing crates.io requirement.

Branch: `cpal-0.19`, off `master` at `a7c6579`. Not for merge until
0.19.0 is released.

## Files Modified

- `Cargo.toml`: `cpal` now `{ git = "https://github.com/RustAudio/cpal",
  optional = true }`, replacing `version = "0.18.2"`, with a comment
  recording that this must revert to a plain `cpal = "0.19"` once
  0.19.0 ships.
- `src/cpal_backend.rs`:
  - `OutputCallbackInfo` -> `CallbackInfo` in the data callback.
  - `stream.play()` -> `stream.start()` (and the error context string).
  - Dropped the `ErrorKind::Xrun` arm from `classify_error`, its
    assertion in `classify_error_buckets`, and updated the
    module-level bucket documentation to explain where xruns went.
  - Replaced the unconditional 50 ms flush sleep in `run_stream`
    with `stream.stop(Some(DRAIN_TIMEOUT))`. New `DRAIN_TIMEOUT`
    const (10 s), sized as a backstop rather than a normal-path
    budget: with `BufferSize::Default` a pipewire-pulse sink can
    choose a pre-buffer of a second or more, and a tighter bound
    would truncate melodies.
  - The abort path deliberately does *not* drain — it falls through
    to `drop`, which cpal documents as halting immediately.
  - The error path also drops without draining; there is no point
    waiting on a stream the backend just declared broken.
  - Removed `stream_cfg.buffer_size = BufferSize::Fixed(..)` and the
    `BufferSize` import, leaving the backend's system-configured
    default. Replaced the workaround comment with one recording why
    the override existed and why it is no longer needed.
- `Cargo.lock`: `cargo update -p bitflags@2.11.1` (see below), then
  cpal 0.18.2 -> 0.19.0 from git at `8f7e77a`.
- `changelog/20260819-cpal-019-upgrade.md` (this file).

## Obstacles and Solutions

**Lockfile conflict on first build.** cpal 0.19 requires
`alsa ^0.12.1`, which requires `bitflags ^2.13.0`, but the lockfile
pinned `bitflags 2.11.1` via `coreaudio-rs`. Resolved with
`cargo update -p bitflags@2.11.1` (the bare `-p bitflags` spec is
ambiguous — 1.3.2 and 2.11.1 are both present). That also pulled
`alsa` 0.11.0 -> 0.12.1 and `alsa-sys` 0.4.0 -> 0.6.1.

**No other migration work was needed.** The build was clean on the
first attempt after the four edits, with no deprecation warnings —
so nothing else in spkrd touches the 0.19 breaking surface.

## Verification

Build, all clean, no warnings: default, `pulseaudio`, `pipewire`,
`jack`, `pulseaudio,pipewire`, `--no-default-features`.

`cargo test`: 25 unit + 5 integration tests pass.
`cargo clippy --all-targets --features pulseaudio,pipewire`: no
findings in `cpal_backend.rs`.

### Runtime — the `BufferSize::Default` revert holds up

Confirmed `buffer_size=Default` in the startup log on all hosts.

Playback timing, `T200 O4 cdefgab>c` (~2.45 s of audio):

| host | request wall time |
|---|---|
| PulseAudio | 2.483 / 2.468 / 2.470 s |
| PipeWire | 2.487 / 2.448 / 2.446 s |

Wall time tracks melody duration, so the audio is played out in full
rather than truncated. This is the direct evidence that #1258's
draining stop does what the `BufferSize::Fixed` workaround used to
do, and the revert is sound.

### Runtime — cancellation is not degraded

The concern behind the rejected option was that a large default
pre-buffer would leave queued audio playing after a client
disconnect. Measured on PulseAudio, aborting a ~10 s melody 1 s in:

- The next request was served **24 ms** after the abort, so
  `play_lock` is released promptly.
- The PA sink-input disappeared **within 0.3 s** of the abort, so the
  audio genuinely stops rather than merely being detached.

Both well inside the ~10 s the melody would otherwise have run. The
abort path's skip-the-drain-and-drop behaviour is doing its job.

### Runtime — no regression in the fork's original bug

15 consecutive plays on PulseAudio: 15/15 HTTP 200, zero WARN/ERROR
lines, `sink-inputs` flat at its baseline of 2, thread count 18 -> 19
(one tokio blocking-pool thread) and then stable.

### Pre-existing ALSA flakiness — NOT a regression

Repeated streams on the ALSA host fail intermittently with
`ALSA function 'snd_pcm_avail_delay' failed with error 'I/O error (5)'`,
after which the request either retries until `--retry-timeout` or
returns 500. First observed on this branch, so it was checked against
`master` in a scratch worktree, same machine, same sequence:

| build | result |
|---|---|
| master (cpal 0.18.2, `BufferSize::Fixed`) | 6/8 succeeded, 5 ALSA I/O errors |
| branch (cpal 0.19, `BufferSize::Default`) | 6/8 succeeded, 5 ALSA I/O errors |

Identical. The failure is pre-existing and independent of both the
cpal version and the buffer-size change. An earlier master run was
in fact *worse* (hung from request 2 onward), but that appears to be
run-to-run variance rather than a real difference.

Untested hypothesis: this machine's "Default Audio Device" is
PipeWire's ALSA compatibility plugin, and repeated open/close cycles
leave it in a bad state. Not investigated further — out of scope for
this branch, and the hosts spkrd actually uses here (PulseAudio,
PipeWire) are unaffected. Worth noting that a plain `cargo build`
with no backend features selects the ALSA host on Linux, so this is
not a purely hypothetical path.

Not verified: suspend/resume and pipewire-pulse-restart recovery
(the `rebuild_device` path). Needs a real suspend cycle.

## Current Status

Branch `cpal-0.19` is complete and verified as far as this machine
allows. Nothing is staged; the user commits.

Before merging, once 0.19.0 reaches crates.io:

1. Change `Cargo.toml` back to a plain `cpal = "0.19"` requirement
   and drop the git dependency.
2. Re-run the timing and cancellation checks above against the
   released crate.
3. Decide separately whether the pre-existing ALSA flakiness is worth
   chasing, and whether `DRAIN_TIMEOUT` at 10 s is the right backstop
   (it is a guess, not a measured bound).
